# project-loop-harness v0.6.0

**Prepared:** 2026-08-11

**Status:** Release candidate verification in progress; not published

**Scope:** terminal authority, isolated proof, and practical opt-in progress guard

## Highlights

- Adds `pcl progress guard activate/status/observe/replan` under the existing
  progress command group.
- Derives Goal/Exit-Gate lineage state deterministically from schema-8 Events;
  no table or migration is added.
- Treats Task/Run/Route/model/VM/cache/dependency/artifact-version changes as
  labels that cannot reset progress.
- Accepts only four behavior-facing value kinds and keeps harness support and
  deferred work separate from product verdicts.
- Stops normal `next`, attached successor creation, and workflow Run/Job
  creation after two consecutive zero-value observations by default.
- Records an explicit operator replan Event without erasing history or consumed
  tokens.
- Ships finish runner observability and hybrid runner-authority anchors with
  fail-closed ordering (independent reviews GO at `f19f36b`).
- Adds exact Task terminal-readiness guards and atomic direct Task acceptance
  without changing schema or completion-packet contracts.
- Keeps clean-Linux retained-root reads descriptor-relative through strict
  Evidence resolution and Task Accept final resealing; root replacement at the
  physical SQLite boundary fails closed without committing either root.
- Adds the C1-C6 local proof chain: authority resolution, isolated exact-commit
  workspaces, deterministic execution, semantic coverage admission, durable
  anchors, and read-only drift eligibility. These layers do not self-authorize
  reuse, release, or a human decision.
- Keeps runner events bounded while atomically refreshing a small overflow
  summary with the latest observed node, phase, completed count, elapsed time,
  heartbeat, overflow state, and exact dropped-event count.

## Compatibility and boundaries

- Activation is opt-in. Existing projects and Goals retain prior behavior.
- DB schema remains **8**; migration count is zero.
- Runtime dependency count remains zero; Python support remains 3.10-3.13.
- Existing C7 proof-reuse and `completion-packet/v1` contracts remain
  backward compatible; no completion-packet schema change is included.
- The guard is cooperative policy enforcement, not malicious-agent resistance.
- It does not block external Cockpit task creation or arbitrary direct DB/file
  edits and does not authenticate the human cryptographically.
- No native helper, telemetry, network service, cloud/hosted state, schema
  migration, runtime dependency, or automatic publication action is included.
