# project-loop-harness v0.6.0

**Prepared:** 2026-08-04

**Status:** Local implementation candidate; not published

**Scope:** practical opt-in Mainline Progress Guard

## Highlights

- Adds `pcl progress guard activate/status/observe/replan` under the existing
  progress command group.
- Derives Goal/Exit-Gate lineage state deterministically from schema-8 Events;
  no table or migration is added.
- Treats Task/Run/Route/model/VM/cache/dependency/artifact-version changes as
  labels that cannot reset progress.
- Accepts only four behavior-facing value kinds and keeps harness support and
  deferred work separate from product verdicts.
- Stops normal `next`, attached successor creation, and workflow Run/Job
  creation after two consecutive zero-value observations by default.
- Records an explicit operator replan Event without erasing history or consumed
  tokens.

## Compatibility and boundaries

- Activation is opt-in. Existing projects and Goals retain prior behavior.
- DB schema remains **8**; migration count is zero.
- Runtime dependency count remains zero; Python support remains 3.10-3.13.
- Existing C7 proof-reuse and `completion-packet/v1` contracts are unchanged.
- The guard is cooperative policy enforcement, not malicious-agent resistance.
- It does not block external Cockpit task creation or arbitrary direct DB/file
  edits and does not authenticate the human cryptographically.
- No process supervisor, artifact seal, native helper, telemetry, network,
  cloud, hosted state, deployment, or publication action is included.
